## 本轮修复

1. 同一计划连续保存造成重复提醒：前端防连点，后台按项目、开售时间、张数、预算和有序备选去重。
2. 切换演出仍沿用旧备选：切换项目 ID 时清空，需要重新填写。保留全局张数与预算，保存前仍可调整。
3. 通知失败却记为已通知：成功、失败、中断不明分开；明确失败允许本人重试。
4. 提醒定时器丢失：后台重新启动时检查，补回未来提醒，补发已过期的待提醒任务。无法保证系统实际展示或准点触发。
5. 手机入口被改写、多轮开售被误选：保留原官方入口，冲突时间保持待核实。
6. 核心接受损坏记录或过期操作：拒绝损坏日志，只接受最近一次有效提案；结果缺失时暂停查单。

47项测试通过，具体证据与未验收范围见 [TEST-REPORT.md](TEST-REPORT.md)。

## 距离“本人只付款”还要补什么？

按下面顺序接入，每个阶段写清支持的真实页面。验证码、登录失效或实名核验仍可能需要本人处理；程序不能保证先锁到票。

| 阶段 | 需要实现 | 通过标准 |
|---|---|---|
| 1. 真实页面样本 | 确定具体演出、电脑/手机网页入口；取得已加载页面的脱敏样本，核实购买入口与平台规则 | 能区分项目、具体场次、票档、开售轮次；App限定时明确不支持网页执行 |
| 2. 只读页面适配器 | 实现 `inspect()`，把真实页面转换成核心识别的快照 | 有票、售罄、未开售、未知、登录/验证/排队均有样本；缺信息返回未知；不凭按钮文字判断锁票 |
| 3. 选择与结算核对 | 实现 `prepare()` 和 `readCheckout()`，核对场次/票档/张数/费用及本机观演人选择 | 唯一匹配才操作，每一步重读页面；预算或身份变化立即停下 |
| 4. 购买后台 | 跨标签单实例、运行代次、持久化购买意图、刷新恢复 | 同一购买任务不能双提交；日志写入失败不点击；旧页面消息不能推动新任务 |
| 5. 提交与订单核对 | 实现 `submitOnce()`、`reconcile()`，关联目标订单与待付款状态 | 超时、断网、跳转不明只查单；确认没有本次订单且售罄后才切备选 |
| 6. 用户本机验收 | 安装扩展、真实采集/提醒、观察模式；之后核验明确配置的购买流程 | 记录支持渠道、页面版本、日期与实际执行范围；付款保持本人操作 |

真实适配器没有样本时，不编造 CSS 选择器、私有接口、服务端签名或验证码判断。下一轮最有价值的输入是一个当前可正常打开的目标演出官方链接及其页面状态；不需要交出密码、Cookie或身份证信息。
