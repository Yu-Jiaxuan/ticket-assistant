# 实现与维护方案

## 产品目标与诚实边界

用户提前在官方网页登录，配置主目标和有序备选；正常流程尽可能只需付款。程序不能保证库存、响应速度或不触发验证。锁票结果需要目标订单、待付款状态、场次、数量和金额全部匹配。选中票档、跳转确认页、出现付款字样都不足以证明成功。

当前原型不是大麦已适配产品。浏览器扩展可直接在已登录标签页运行，避免传输登录凭证；现有扩展仅作页面观察。核心与模拟页面用于验证未来真实适配器的决策规则。不会自动下载或执行远程规则。

## 真实适配器的边界与接口

后续实际页面适配器须提供以下接口，当前没有伪造实现：

- `inspect()`：给出明确的项目/场次/票档身份、登录/排队/验证状态、页面版本、已有待付订单，以及每个候选的 `available / soldout / notopen / unknown` 状态。
- `prepare(choice, quantity)`：仅在准确识别元素且唯一匹配时选择票档与数量；每个步骤后重新检查身份与页面状态。不得用坐标盲点，不得省略张数、费用与观演人校验。
- `readCheckout()`：从官方结算页面读取项目、场次、票档、张数、含费用总价；对比配置。观演人仅在本机处理，不写日志。
- `submitOnce()`：持久化提交意图后只提交一次。网络超时、页面跳转未知、DOM 丢失、验证码、服务端响应不明均归入不确定状态。
- `reconcile()`：只读核对官方订单。有匹配待付订单则成功；只有明确确认本次未形成订单才能继续尝试。仅“订单列表暂时为空”不能证明没有在途订单。

生产版必须将单实例锁、持久化记录和运行代次放入扩展后台，作用域覆盖所有购买标签页。模拟用 Web Locks + localStorage 验证此思路，不等同于生产扩展后台实现。提交日志必须关联账号的本机匿名标识、项目和一次运行；持久化失败时不点击提交。

## 决策过程

1. 启动前校验配置、演出入口、时间与预算、登录和已存在订单。
2. 优先观察 DOM 自行更新；如将来确有获准查询方式，单独配置平台允许的频率，不假定通用安全请求间隔。
3. 首选 `available` 才进入准备。首选 `soldout` 才看后一个；首选 `unknown` 暂停，`notopen` 等待。
4. 结算前再次检查含费用总价、场次、张数、观演人选择以及页面状态。
5. 持久化 `SUBMITTING` → 提交一次 → 核对结果。成功后停止所有其他购买。
6. 明确无订单且售罄，回到优先级决策；不确定则记 `UNKNOWN`，停下等待核对，不直接重试。
7. 付款由本人完成。停止按钮只阻止新操作，不能撤回已经发往平台的请求。

## 已知问题及维护处理

| 情况 | 处理 | 当前验证范围 |
|---|---|---|
| 下单弹验证 | 暂停本人处理，随后先核对订单 | 模拟 |
| 登录失效 | 暂停登录，不能继续点击 | 模拟 |
| 排队/风控 | 停止自动动作；不另建请求绕队 | 模拟 |
| 票档看似有票，提交售罄 | 明确没有订单才能切备选 | 模拟 |
| 提交超时但服务端已成功 | 记 UNKNOWN，只读查单 | 模拟 |
| 已有未支付订单 | 先人工核对，不抢第二单 | 模拟 |
| 价格变化/多选张数 | 结算校验不匹配即暂停 | 核心测试 |
| 页面版本或选择器改变 | 唯一性与结构契约不满足即停 | 模拟；真实契约待采集 |
| 多标签/重复启动 | 单实例锁＋持久化提交意图 | 演示实现；扩展购买后台待实现 |
| 页面刷新/进程崩溃 | 历史 SUBMITTING/UNKNOWN 不重试 | 核心及演示 |
| 浏览器后台节流 | 不承诺实时；用户保持页面可见 | 明确限制 |
| App 限定入口 | 不假设网页可代替；重新评估渠道 | 待目标项目核实 |

## 后续维护方法

每次收到故障，记录版本号、购票渠道、停在哪个状态、脱敏错误提示和是否存在订单；不索要密码、Cookie、验证码或完整身份证。先在匿名固定页面重现，再修改相应适配器或状态机，加入针对此故障的回归测试，再在用户本机观察模式验收。

版本发布明确标注：支持的具体渠道、项目或页面版本、最近验证时间、是否执行过真实订单测试。页面不匹配默认停止。没有后台托管或定时维护任务；不会承诺无人值守持续更新。此处“维护”指当前故障防护和后续可复现修复流程。
